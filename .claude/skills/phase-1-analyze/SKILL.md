## 🧭 Phase state marker (v4.67.1+)

На входе в фазу **обязательно** зафиксируй machine state:

```bash
node .claude/skills/status/references/phase-state.mjs start 1
```

Если дошёл до STOP-point и ждёшь решение пользователя — запиши причину перед ответом:

```bash
node .claude/skills/status/references/phase-state.mjs block 1 "KPI Floor/Target/Stretch + 3-month content budget approval"
```

Только после всех штатных gate/проверок и обязательных решений пользователя отметь выход фазы:

```bash
node .claude/skills/status/references/phase-state.mjs complete 1 wiki/architecture/metrics.md wiki/design/brief.md
```

Marker не заменяет evidence и не разрешает перескочить STOP-point. `/status` использует его как
machine-readable progression state, а сами артефакты остаются доказательством результата.
Команда `complete` сама отклоняет отсутствующие evidence-файлы, незаполненный бриф, числовые KPI
без URL-источника/явной метки «гипотеза» и отмеченные выполненными runtime-критерии при отсутствии
реального кода. При отказе marker остаётся `blocked`, Git checkpoint и удалённый push не выполняются.
В `wiki/research/*.md` ссылка/локальный источник либо `TBD/не проверено` указываются на той же строке,
что и внешний факт. Общая приписка «источников нет» в начале документа не разрешает ниже писать
конкурентов, даты или рыночные выводы из памяти модели.


**Модели:** Claude `opus`. Codex `gpt-5.6-sol/high`; route `metrics-conflict` →
`gpt-5.6-sol/xhigh` только при противоречивых источниках или KPI/content-budget.
Канон: `status/references/model-policy.json`; Max/Ultra автоматически не включать.


Проходит целиком: прототип → wiki → метрики с контент-бюджетом.

1. `/analyze-project <папка>` — занести прототип (HTML+концепт), завести wiki.

## 🎤 БРИФ — обязательный минимум вопросов ПОСЛЕ анализа прототипа

Прототип прочитан, что в нём есть — понятно. Теперь то, что из кода НЕ узнать и что определяет
всё дальнейшее. Спроси коротко, одним раундом по формату `/grilling` (нумерованные вопросы,
у каждого рекомендованный ответ):

1. **Аудитория** — возраст и кто это. Меняет темп, сложность, подачу текста, объём туториала
   и возрастной рейтинг в черновике. Сейчас это всплывает только в Ф6, когда игра уже сделана —
   поздно.
2. **Амбиция** — проба пера на 2 недели или всерьёз на 3 месяца? От этого зависит, сколько
   дефицита имеет смысл закрывать, а сколько — резать.
3. **Обещание игры** — что игрок должен ПОЧУВСТВОВАТЬ. Не «тактическая стратегия», а
   «объявить войну клану и сидеть до ночи». Из этого потом растёт вся математика удержания.
4. **Отличие** — чем эта игра не такая, как десяток похожих в каталоге.
5. **История** — что уже пробовал и что не сработало (если прототип не первый).

**Ответы записать в `wiki/design/brief.md`.** Фазы 2-6 читают его оттуда и НЕ переспрашивают:
аудитория → сложность и рейтинг, амбиция → скоуп, обещание → фичи по дням, отличие → листинг
и креативы.

**Полный `/grilling`** (45 минут, всё дерево решений) — по запросу пользователя или когда после
брифа осталось много неопределённого: скажи об этом прямо и предложи, но не запускай сам.

## 🎯 Целевые метрики — ИЗ ВНЕШНЕГО МИРА, не из своих прошлых игр

**По другим проектам пользователя НЕ ходить.** Свои прошлые цифры — это твой потолок, а не
ориентир: увидел D7=6% в прошлой игре — поставишь 6-7% и спроектируешь контент ровно на
повторение прошлого результата. Замкнутый круг.

**Куда смотреть на самом деле:**
1. **Топ жанра в каталоге платформы** — что там в лидерах, сколько игр в категории, какой
   заявленный плейтайм, что пишут в отзывах (жалобы = чего не хватает всем);
2. **Интернет по жанру**: разборы, постмортемы, публичные цифры удержания похожих игр,
   отраслевые бенчмарки (типовые D1 30-40% / D7 10-15% / D30 3-5% для казуалок; у игр с
   длинным прогрессом D1 ниже, D7 выше);
3. **Прямые конкуренты** — 2-3 игры, ближе всего к задуманной: чем держат, что в мете,
   на чём зарабатывают.

В `metrics.md` цель пишется **диапазоном и с указанием источника**: «D7 8-12% (ориентир по
жанру: <источник>, дата)». Голое число без источника = 📏 гипотеза (см. ядро).

Исключение: пользователь САМ дал цифры своих игр или прямо попросил на них ориентироваться.

## 📐 РАЗМЕРНОСТЬ ИГРЫ — установить в фазе 1 (влияет на всё дальше)

2D / 2.5D / 3D определяет стек, арт-пайплайн, фильтр библиотеки ассетов, бюджет
производительности и требования к слабым Android. Дальше её знать ОБЯЗАНЫ фазы 3, 4 и 5.

**Есть прототип → определи фактом, не спрашивая:**
```
grep -l "three\.\|WebGLRenderer\|babylon\|PlayCanvas" <игра>/**/*.js   → 3D
grep -l "getContext(['\"]webgl" <игра>/**/*.js                            → 3D/WebGL
grep -l "getContext(['\"]2d" <игра>/**/*.js                               → 2D canvas
изометрия/псевдо-3D спрайтами                                            → 2.5D
```
**Прототипа нет (старт с концепта) → 🔴 РЕШЕНИЕ ПОЛЬЗОВАТЕЛЯ:**
```
🔴🔴🔴 ТРЕБУЕТСЯ ТВОЁ РЕШЕНИЕ [Ф1 анализ]
Вопрос: размерность игры? От неё зависят стек, ассеты и производительность.
  А) 2D (canvas) — лёгкий вес, мгновенная загрузка, слабые Android тянут, ассетов больше всего
     в библиотеке. Дефолт для веба.
  Б) 2.5D (изометрия спрайтами) — объём картинки при 2D-цене; арт дороже (углы/направления)
  В) 3D (three.js) — тяжелее по весу и GPU, риск на слабых Android, /three-setup обязателен
Моя рекомендация: <по жанру и платформе>
⏸ Работа ОСТАНОВЛЕНА до ответа.
```
**Записать результат** в `wiki/_map.md` строкой `**Размерность:** 2d|2.5d|3d` — фазы 3-5
читают её оттуда и НЕ переспрашивают.
