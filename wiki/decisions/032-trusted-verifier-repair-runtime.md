# Решение: проверки исполняет доверенный runtime, а не модель или проект

**Дата:** 23.08.2026 · **Версия:** v4.68.43

## Ситуация

Граф v4.68.42 уже различал узлы `implement`, `verify` и `repair`, но сам запуск проверок оставался
ручным. Модель могла остановиться на `verify`, интерпретировать длинный stdout неверно или предложить
собственный скрипт под видом verifier. Автоматическое исполнение из реестра проекта также дало бы
ему возможность подменить запускаемый код.

## Решение

1. `Task.verifiers` содержит не команды, а не более 20 точных ID из реестра установленного Forge.
2. Исполняются только записи с явным `taskRunner`, `scope: project` и `mutates: false`.
3. Project-local registry не доверяется. Test fixture может передать иной реестр только через
   отдельную internal API-опцию, которую production CLI не выставляет.
4. `verificationTarget` обязан быть project-relative и не выходить из корня проекта.
5. Узел `verify` принадлежит runtime: PASS ведёт в `done`, exit 1 нормализуется в
   `VERIFIER_FAILURE` и ведёт в `repair`, timeout/exit 2 ведёт в infrastructure `blocked`.
6. Нормализованный `RunResult.verification` хранит ограниченный список checks/issues; сырой
   неограниченный stdout не становится контекстом агента.
7. Один Task verifier защищён token-owned lock. Активный или устаревший lock не перехватывается
   автоматически: без переносимого filesystem CAS это создало бы гонку двойного запуска.
8. Host может настроить план только пока Task находится в agent-node. GigaChat выводит план гачи
   только из точной успешной канонической команды своего durable ledger.

## Последствия

- `implement → verify → repair → verify` работает одинаково для adapters, использующих общий runtime.
- Ошибка проверки расходует общий ограниченный repair budget, инфраструктурная ошибка — нет.
- Проект или текст модели не могут расширить исполняемую поверхность.
- Stale lock требует осознанной проверки процесса и ручного удаления; это намеренный выбор в пользу
  отсутствия параллельного исполнения.
- Task scope пока остаётся декларацией; file leases и write-boundary enforcement — следующий слой.
