# Интеграция GigaChat с Project Forge: что сделано и что достигнуто

**Состояние на:** 19 августа 2026 года  
**Версия Forge:** 4.68.26  
**Модель в испытаниях:** GigaChat-3-Ultra через API

## Краткий итог

Мы превратили GigaChat из обычного диалогового API в терминального участника Project Forge: модель получает текущую фазу, ограниченный набор инструментов, состояние проекта и обязательные проверки. На хорошо ограниченных и заранее модульных задачах связка уже способна довести изменение до проверенного результата. Как полностью автономный разработчик новой игры только по GDD она пока ненадёжна.

Практический вывод: GigaChat можно использовать для анализа, проектирования, принятия решений и ограниченных операций над кодом. Для длинной автономной реализации необходимы более специализированная coding-модель, жёсткие операции Forge и независимые верификаторы.

## Задача интеграции

Целью было научить GigaChat работать внутри того же девятифазного процесса, который Forge предоставляет другим ИИ:

1. анализ идеи и проекта;
2. GDD и планирование;
3. подготовка реализации;
4. визуальная часть;
5. разработка;
6. контент и платформенная подготовка;
7. QA;
8. сборка и выпуск;
9. последующее развитие.

Важно было не просто получать текстовый ответ, а дать модели безопасный доступ к проекту: чтение и изменение файлов, выполнение разрешённых команд, поиск, браузерное тестирование, фиксацию решений и продолжение после остановки.

## Что построено

### 1. Собственный терминальный адаптер Forge

Forge напрямую обращается к GigaChat API и переводит канонические фазы в понятный модели формат. Адаптер предоставляет функции для файлов, команд, фазовых гейтов, доказательств, поиска, диагностики и специальных операций. Секреты хранятся вне проектов.

Это не GigaCode CLI: сейчас код выполняет общая модель GigaChat-3-Ultra через разработанный нами слой инструментов.

### 2. Долговременное состояние фаз

Решения пользователя, STOP-точки, текущая фаза, результаты research и evidence сохраняются на диске. После перезапуска или сокращения контекста адаптер восстанавливает реальное состояние, а не просит модель угадывать, где она остановилась.

Исправлены сценарии с частично сохранёнными ответами Q1–Q5, повторным открытием уже принятых решений и потерей владельца STOP-точки.

### 3. Понятные ответы на пользовательских гейтах

Каждая обязательная остановка теперь объясняет, что именно нужно решить и как ответить. Полный набор рекомендаций можно принять коротким словом `утверждаю`; изменения передаются по предложенному шаблону. Естественные фразы вроде `принимаю рекомендации` также распознаются, если в них нет оговорок.

### 4. Прямой режим реализации

Добавлена команда `/do <задача>` и сопутствующие `/task`, `/resume-phase`. Прямая задача хранится отдельно от фазового автопилота, переживает сокращение контекста и имеет приоритет над устаревшим продолжением фазы. Пока она активна, модель механически не может самовольно перейти к релизу или другой фазе.

### 5. Завершение только по реальным доказательствам

Фраза модели «готово» больше не считается результатом. Forge принимает завершение только при наличии успешных проверок, выполненных после начала текущей задачи. Статусные вопросы остаются read-only, поддельные проверяющие скрипты внутри рабочей папки не принимаются как доказательство.

### 6. Локальная поведенческая диагностика

Forge записывает обезличенные JSONL-события о проблемах поведения модели, адаптера и инструментов. События очищаются от секретов, дедуплицируются по стабильному fingerprint и могут быть собраны единым аудитором по всему локальному парку проектов.

### 7. Защита крупных игр от разрушительных перезаписей

После реального случая, когда попытка добавить механику уменьшила существующую игру с 93 КБ до 17 КБ, появились:

- автоматическое постраничное чтение, переживающее сокращение контекста;
- запрет слепой реконструкции крупных существующих файлов;
- контроль подозрительного уменьшения файла;
- лимит полных перезаписей одного пути;
- ограничители циклов чтения и compaction;
- чистый повтор явной `/do`-задачи после безопасной остановки.

### 8. Детерминированная модульная работа

Для монолитов больше 32 КБ или 800 строк Forge сначала выполняет проверяемое разбиение. Исходный порядок выполнения и общая браузерная область видимости сохраняются. Создаются резервная копия и hash-bound контракт модулей в `wiki/architecture/`.

После изменения контракт можно безопасно обновить: пути, порядок и границы модулей не разрешается незаметно менять. Для межмодульных возможностей предусмотрены атомарные Forge-операции и узкие целевые проверки.

### 9. Неизменяемые версии сборок

Каждая новая сборка получает более высокий номер и новый набор ZIP-архивов. Существующий архив нельзя перезаписать и выдать за новую версию.

## Подтверждённые результаты

### Phase 1 resume-orchestrator

Изолированный реальный прогон восстановления первой фазы прошёл 19 из 19 проверок. Адаптер восстановил решения и evidence из долговременного состояния без повторного анализа и без повторного расхода модельного вызова.

### `testgigachat-v4`: модульная интеграция гачи

Монолит размером 93 367 байт и 2 549 строк был детерминированно преобразован в оболочку, CSS и 17 JS-модулей. Затем GigaChat выполнил явную `/do`-задачу через атомарный интегратор. Итоговая проверка включала:

- контракт из 20 подключённых файлов;
- отсутствие потерянных и сиротских модулей;
- целевой тест механики merge-grid/gacha;
- сохранение и восстановление состояния;
- поведение полной очереди;
- F5-сценарий;
- 25 кликов в браузерном playtest;
- отсутствие runtime- и console-ошибок на локальной стадии.

После доказанного завершения адаптер остановился и не начал самовольно Phase 8.

### Новый проект только из GDD: Snake

Эксперимент `gdd-snake-gigachat` стартовал без `index.html` и без игрового кода. GigaChat смог создать HTML, CSS, модули и заготовки контрактных тестов, то есть greenfield-старт из одного GDD технически возможен.

Однако готовой рабочей игры без вмешательства получить не удалось. В разных попытках были обнаружены неподвижная змейка, неработающее изменение направления, потерянные touch-контролы, отсутствие fullscreen, неверный путь теста и обрезанные JS-модули. Защитные механизмы остановили дальнейшее повреждение, но не смогли заменить отсутствующую coding-надёжность модели.

## Честная оценка зрелости

| Сценарий | Состояние |
|---|---|
| Анализ, вопросы, рекомендации, GDD | Работает при долговременном состоянии и явных гейтах |
| Продолжение фазы после STOP | Работает, покрыто регрессиями |
| Ограниченное изменение небольшого модуля | Работает с целевой проверкой |
| Изменение большой существующей игры | Работает только после модульного разбиения и с защитными операциями |
| Полностью автономная игра из одного GDD | Пока не доказано; эксперимент завершился неработающей сборкой |
| Самостоятельная оценка готовности моделью | Ненадёжна; требуется внешний evidence gate |
| Длинная свободная работа с большим объёмом кода | Высокий риск потери контекста и повреждения файлов |

## Зачем нужен GigaCode CLI

GigaChat-3-Ultra и GigaCode решают разные задачи. Ultra полезен как универсальная рассуждающая модель, но наше тестирование показывает, что одной общей модели недостаточно для устойчивого длинного coding-loop.

Предпочтительная архитектура:

1. GigaChat-3-Ultra анализирует проект, формирует GDD и план, объясняет решения пользователю.
2. GigaCode CLI реализует конкретный ограниченный модуль и запускает тесты.
3. Forge хранит состояние, управляет инструментами и блокирует опасные переходы.
4. Независимый верификатор проверяет реальное поведение в браузере.

Такой подход позволит использовать сильные стороны обеих моделей и не считать уверенный текст доказательством работающего кода.
