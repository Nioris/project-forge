# GigaChat + Project Forge: проблемы, причины и исправления

**Период наблюдений:** август 2026 года  
**Срез Forge:** 4.68.26  
**Назначение:** инженерный postmortem и материал для обсуждения с командой GigaChat/GigaCode

## Резюме

Основная проблема оказалась не одной ошибкой, а сочетанием четырёх слоёв:

1. общая модель нестабильно выполняет длинные цепочки coding-tool вызовов;
2. ранний адаптер недостаточно жёстко восстанавливал состояние и маршрутизировал намерение;
3. текстовые обещания модели принимались раньше, чем появлялись реальные доказательства;
4. крупные монолитные игры не помещались в безопасный рабочий контекст.

Большинство дефектов оркестрации закрыто или ограничено механическими guard-ами Forge. Остаточный риск теперь лучше виден: GigaChat-3-Ultra способен выполнить узкую доказуемую операцию, но всё ещё может написать логически неверный или обрезанный код при автономной greenfield-разработке.

## Методика и источники

Разбор основан на:

- локальных JSONL-диагностиках Forge;
- регрессионных тестах адаптера и реальном GigaChat API entrypoint;
- истории исправлений 4.68.7–4.68.26;
- проекте `testgigachat-v4` с существующей игрой размером около 93 КБ;
- greenfield-проекте `gdd-snake-gigachat`, созданном только из GDD;
- независимых браузерных проверках, а не только ответах модели.

Срез аудитора за 30 дней по `F:\ProjectForgeUniversal`:

| Показатель | Значение |
|---|---:|
| Просканировано проектов | 29 |
| Проектов с журналами | 3 |
| Всего событий | 396 |
| Открытых fingerprint-групп | 49 |
| Critical / Error / Warn групп | 2 / 17 / 30 |

`Открытая группа` — это дедуплицированный fingerprint, а не отдельный сбой и не доказательство, что дефект до сих пор воспроизводится в текущей версии. Старые группы могут оставаться без события resolution после исправления кода.

## Что показали журналы

### Текстовые имитации инструментов

В 396 событиях доминируют предупреждения о malformed textual tool calls. Наиболее заметные группы по числу зафиксированных событий:

| Инструмент | Событий |
|---|---:|
| `forge_script` | 62 |
| `read_file` | 47 |
| `run_command` | 42 |
| `forge_memory_update` | 36 |
| `write_file` | 28 |
| `forge_gate` | 26 |
| `ask_user` | 15 |
| `replace_text` | 13 |
| `search_text` | 10 |

Адаптер обычно смог восстановить такой вызов. Поэтому эти числа не равны числу сорванных задач, но показывают, что native tool-calling остаётся нестабильным и требует дополнительного слоя совместимости.

### Ошибочные заявления и циклы

Аудитор видел пять fingerprint-групп `GIGA_UNVERIFIED_COMPLETION_CLAIM`, циклы чтения в двух проектах, runtime exceptions, пустые ответы в фазах 1–8 и отдельные нарушения STOP/gate-контекста. После выпусков 4.68.20–4.68.26 критические переходы перенесены из prompt-инструкций в механические ограничения адаптера.

### Что не относится к GigaChat

Ошибка локального MCP `127.0.0.1:8091` в проекте `neftistan` происходила в Codex-сессии и не является доказательством проблемы GigaChat. Она должна учитываться отдельным host-профилем диагностики.

## Что реально исправлено, а что только ограждено

**Исправлено в Forge:** восстановление фаз и STOP, UX ответа, приоритет `/do`, запрет самовольного релиза, доверенная цепочка evidence, уникальные версии сборок, модульный контракт.

**Ограждено, но не исправлено в модели:** текстовые tool calls, пустые ответы, потеря качества на длинном контексте, преждевременная уверенность и повреждение кода. Forge теперь распознаёт или останавливает эти случаи, но не делает базовую модель более сильным программистом.

**Остаётся доработать в Forge:** управляемый lifecycle локального сервера, recovery после заблокированной перезаписи, обязательный dynamic-import/browser syntax gate, корректный keyword classifier и allowlist bootstrap-проверки секретов.

## Рекомендованная архитектура следующего шага

```text
Пользователь
    ↓
GigaChat-3-Ultra — анализ, GDD, план и решения
    ↓ ограниченная задача + контракт
GigaCode CLI — реализация и локальные тесты
    ↓ файлы + логи + код возврата
Forge — состояние, guards, Git, версии и маршрутизация
    ↓
Независимый browser/verifier gate
```

Ключевой принцип: модель, написавшая код, не должна единолично подтверждать его готовность.

## Минимальные сценарии для совместного воспроизведения

### Сценарий A: стабильность native tools

Дать модели 30 последовательных операций чтения, точечной записи и запуска команды. Зафиксировать долю настоящих function calls, текстовых имитаций, пустых ответов и повторов.

### Сценарий B: восстановление после compaction

Открыть файл больше 90 КБ, найти символ после 2 000-й строки, сократить контекст и запросить точечное изменение. Проверить, продолжает ли модель чтение с durable cursor и сохраняет ли остальной файл побайтно.

### Сценарий C: greenfield из GDD

Передать GDD простой Snake без исходного кода. Критерии: реальный timer-loop, направление, столкновения, рост, счёт, touch, fullscreen, reload save, dynamic import и Playwright. Запретить завершение до прохождения каждого критерия.

### Сценарий D: ложная готовность

Создать визуально открывающуюся, но неподвижную игру. Проверить, потребует ли агент runtime-свидетельство движения состояния, а не ограничится отсутствием console errors.
